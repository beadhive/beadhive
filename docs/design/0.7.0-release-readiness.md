# 0.7.0 release-readiness pass

Record of the pass bh-kxsz.1 required: walk the two paths 0.7.0 actually changes, against a
host that did not develop them, before tagging.

Run 2026-08-02 against `main` after all seven bh-kxsz blockers landed. Both paths were exercised
with an isolated `BH_HOME` (a temp dir), against the **real** `briancripe/beadhive-hq` remote —
so the fleet data is genuine, but nothing was written to the fleet roster.

## Verdict

Both paths work. Two gaps found, neither a blocker; both recorded below and filed.

## PATH 1 — upgrade from a 0.6.0-era host

Simulated by scaffolding a fresh home and deleting `host.yaml` (host identity minting is a
0.7.0 feature — a genuine 0.6.0 home has a flat `config.yaml`, no `fleet.yaml`, no `host.yaml`,
no HQ).

| Step | Result |
|---|---|
| `bh config validate` with no `host.yaml` | ✅ passes |
| `bh host list` / `bh hive list` with no `host.yaml` | ✅ degrade cleanly ("no hosts registered") — no crash on missing identity |
| `bh hq clone` against the real remote | ✅ cloned + hydrated 35,951 chunks |
| Host config vs. the cloned `fleet.yaml` | ✅ **auto-reconciled — 14 stale fleet keys dropped, and announced** |
| `bh config validate` after clone | ✅ passes |
| Fleet inheritance | ✅ `delimiter` resolves to `:` — the FLEET value, after the host's stale copy was dropped |
| `bh hq bd ready` | ✅ 627 ready issues |

The reconciliation is the one that matters. Before bh-w2u9, this exact sequence left the host
permanently unloadable — every later `config.load()` raised, i.e. effectively every `bh`
command. The keys dropped were precisely those the bead predicted:

```text
schema_version, delimiter, providers, exclude.orgs, exclude.repos,
dimensions.component.description, dimensions.size.description, dimensions.size.values,
dimensions.tag.description, worktrees.ephemeral, worktrees.bead_branch,
worktrees.session_branch, worktrees.rmdir_empty, worktrees.init
```

## PATH 2 — second-host adoption

`bh host provision --role worker --dry-run --auto`, against the same isolated home after the
clone above (i.e. a genuinely partial state).

The ordered plan came back correct and, importantly, **resumable**: steps 3 (`hq.remote`) and 4
(`hq clone`) reported `•` skipped-already-done rather than redoing them, and the verify gate at
step 8 correctly reported `✗` because host identity, roster registration, and `.beads`
permissions were not yet in place. That is the "idempotent and resumable against any partial
state" acceptance criterion demonstrated against real partial state, not a fixture.

The `chmod 700` step correctly identified the `.beads` dir — the same nag observed on
factory-orca.

**Not exercised:** the write half (`bh host provision` for real, then `bh host retire`). That
registers a manifest in the live fleet roster, and a failed cleanup would leave exactly the
orphan bh-salu exists to prevent. Deliberately left for the operator to run on the real second
host, which is the only place it proves anything anyway.

## Gap 1 — `bh setup check` is an undocumented prerequisite

`bh host provision` — the recommended entry point for a new host — is gated:

```text
✗ `bh host` requires setup — run `bh setup check` first.
  Skip with BH_SKIP_SETUP_CHECK=1 (debug bypass).
```

Running `bh setup check` once clears it (the result is cached), so this is a required first
step rather than a dead end, and the error names the fix. But the adoption sequence documented
anywhere else does not mention it, and `provision`'s own 8-step plan starts at `config init` —
one step after the thing that blocks it from running at all.

Either `provision` should absorb the check as step 0, or every documented adoption sequence
must start with `bh setup check`. Filed as bh-1kzc.

## Gap 2 — provision's `--dry-run` needed no bypass, but the gate fires before the plan

Minor and related: the setup gate fires before `--dry-run` is honored, so even a zero-mutation
preview is blocked on a fresh host. A preview that changes nothing is the safest possible thing
to allow a new operator to run.

## What a 0.6.0 → 0.7.0 upgrade actually requires

1. `bh setup check` — once, clears the tool gate (Gap 1)
2. `bh config split` — flat `config.yaml` → `fleet.yaml` + reduced host config, **only on the
   host that FOUNDS the fleet**
3. On a host JOINING an existing fleet, no manual split is needed: `bh hq clone` reconciles the
   host config automatically and says what it dropped
4. `bh host init --role <primary-default|worker>` (or `bh host provision`, which does the whole
   sequence)

Machine-local state that must never be copied between hosts: `~/.beadhive/host.yaml`. See
`docs/design/beadhive-home-layout-contract.md` for the full durable / regenerable /
machine-local / artifact classification.
