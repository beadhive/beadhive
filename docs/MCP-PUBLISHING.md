# MCP registry and directory upkeep

`bh-mcp` is the stdio MCP entry point in the PyPI package `beadhive`. The registry name is
`io.github.beadhive/beadhive`. The root [server.json](../server.json) declares the package,
transport, release version, and an explicit client configuration in the schema-supported
`io.modelcontextprotocol.registry/publisher-provided` metadata extension.

## Launch configuration

The package name and executable differ. For this change's 0.24.0 version, the explicit
launch command is:

```sh
uvx --from beadhive==0.24.0 bh-mcp
```

For Beadhive installed on PATH, `clientConfiguration.mcpServers.bh` in `server.json` sets
`command` to `bh-mcp` and `args` to an empty array. The separate
`uvxClientConfiguration.mcpServers.bh` entry runs `uvx` with `--from`, `beadhive==0.24.0`,
and `bh-mcp` as separate arguments. Read the current package pin from `server.json` after
future releases. Configure the normal Beadhive workspace before using
tools that access hives.

The official 2025-12-11 registry schema has no PyPI executable-selection field. Consumers
that infer the executable from the package identifier may attempt `uvx beadhive`, which is
not this server's launch command. Publisher metadata provides the explicit configuration;
generic registry automatic launch is **not verified**. Upstream
[issue 1629](https://github.com/modelcontextprotocol/registry/issues/1629) and
[proposal 1672](https://github.com/modelcontextprotocol/registry/pull/1672) describe the
executable-selection limitation; the proposed field currently targets npm. Avoid relying
on client-specific ordering of `runtimeArguments` to select a Python executable.

## Release and ownership

The [official PyPI requirements][package-types] verify `mcp-name: io.github.beadhive/beadhive`
in the package README served by PyPI. The ownership comment in README.md becomes that package
metadata on the **next** PyPI release; adding it to GitHub does not update an existing release.

The Commitizen pre-bump hook updates `server.json` and its explicit client package pin alongside
`pyproject.toml` and `uv.lock`. The release transaction includes `server.json` in its permitted
version artifacts. To repair metadata after a manual project-version edit, run:

```sh
python3 scripts/sync-mcp-version.py
python3 scripts/sync-mcp-version.py --check
```

The release workflow checks the tag against the project and registry versions before building.
Its `mcp-registry` job waits for successful PyPI publication, verifies the versions again, installs
MCP publisher v1.8.1 with its published SHA256, and authenticates with GitHub Actions OIDC using
`id-token: write`. It then runs `mcp-publisher publish server.json`, following the
[official CI authentication guide][github-actions]. It skips branch-only manual workflow runs.

For an operator's manual publication, install the official publisher and run from the checkout:

```sh
brew install mcp-publisher
python3 scripts/sync-mcp-version.py --check
mcp-publisher login github
mcp-publisher publish server.json
curl --fail --get --data-urlencode 'search=io.github.beadhive/beadhive' \
  https://registry.modelcontextprotocol.io/v0/servers
```

For `io.github.beadhive/*`, interactive GitHub authentication requires an **Owner** of the
Beadhive organization, according to the [official authentication guide][authentication]. A
classic PAT needs `read:org`; a fine-grained PAT needs organization Members read permission.
The Actions job uses OIDC instead of a stored PAT. Publish only after PyPI serves the matching
version and ownership proof. Confirm the listing's package version in the registry response.
This change prepares publication; a live official listing remains **pending operator action**.

## Directory actions

- **Context7:** open [Add library](https://context7.com/add-library), enter
  `https://github.com/beadhive/beadhive`, and complete the form. There is no badge or CLI
  submission step in this change.
- **Glama:** find Beadhive under [MCP servers](https://glama.ai/mcp/servers), then choose
  **Claim ownership** on its listing. If it is not listed, use **Add MCP Server** with the
  GitHub repository URL, display name, and description. For an organization-owned source
  repository, [Glama's server ownership instructions][glama] require a root `glama.json`
  using the schema `https://glama.ai/mcp/schemas/server.json` and a `maintainers` array of the
  claiming operator's actual GitHub username. Commit that operator-specific file and repeat
  the claim flow. After ownership is verified, copy the badge generated by the listing;
  do not invent a badge or add it before a listing exists.
- **GitHits and DeepWiki:** their exact README badges are present. Check indexing after merge;
  GitHits indexing is a follow-up within a week. A DeepWiki page and refresh depend on that
  service's indexing. Local HTTP verification may be blocked by its Vercel checkpoint.

No directory submission or ownership claim is performed by these repository changes. Glama
claiming and any generated badge remain pending. Smithery and PulseMCP submissions are outside
this change's scope.
