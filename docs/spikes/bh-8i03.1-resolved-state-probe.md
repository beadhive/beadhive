# Spike `bh-8i03.1` — can one script dump resolved harness + `bh` state as stable JSON?

**Bead:** `bh-8i03.1` · **Seat:** `dev/dev1` · **Type:** research-only (no product code)
**Feeds decision on:** `bh-8i03.2` (Linux baseline capture, which runs this exact script
unmodified) and, downstream, `bh-8i03.7` (the cross-platform GO/NO-GO decision), which both
depend on this instrument existing and being trustworthy.

## Question

Can a single script, run identically on macOS and Linux, ask the Claude Code harness and
`bh` for their own **resolved** state — not their declared config — and emit it as JSON that
is stable enough to diff two hosts (or two runs of the same host) meaningfully? Concretely,
per bh-8i03.1's acceptance criteria:

- does an introspection surface exist for each of the eight things the parent epic's design
  requires (skills/plugins/agents resolved, MCP connect-vs-declared, hook command
  resolution, effective settings, env vars, binary resolution, `bh`'s own resolved
  workspace/hives/worktree-root, filesystem case-sensitivity), and where it does not, can
  that gap be captured as an explicit, first-class finding rather than a silent omission?
- can the output be made byte-identical across two runs on the same, unchanged host (the
  "zero self-delta" requirement) without asserting anything about a *second* host?
- can MCP servers that actually **connected** be told apart from servers that are merely
  **declared**, including the specific "declared but dead" failure mode?

This bead is explicitly **not** asking whether cross-platform config portability is a GO or
a NO-GO — that is `bh-8i03.7`'s question, after `bh-8i03.2`–`.6` gather comparison evidence
across two real hosts. This bead only has to prove the *instrument* works, on the one host
available to it (macOS).

## Method

1. Read this bead's brief and acceptance criteria, then the parent epic `bh-8i03`'s `design`
   field in full (the six-class classification axis and the "probe resolved state, not
   files" method) to understand what the eventual comparison needs from this instrument,
   even though building that comparison is out of this bead's scope.
2. Read `docs/spikes/TEMPLATE.md` and one worked example (`bh-a7so.1-harness-wire-format.md`)
   for doc convention before writing anything.
3. Rather than assuming what the harness/`bh` can introspect, **probed the tools themselves
   first**, live, one surface at a time, before writing any code:
   - `claude --help`, `claude mcp --help`, `claude plugin --help`, `claude plugin list
     --help` to find which subcommands exist and which support `--json`.
   - `claude doctor`, `claude --version`, `claude plugin list --json`, `claude plugin
     details <name>`, `claude mcp list`, `claude mcp get <name>` — read their real output
     shapes on this host before deciding how (or whether) to parse them.
   - `bh --help`, `bh config show --help`, `bh doctor --help`, `bh hive list --help`,
     `bh worktree --help` — same approach for `bh`'s own introspection surface.
   - Tried `claude config list` expecting a settings-introspection command; there is no
     `config` subcommand in this CLI version, so the bare string `config list` was instead
     interpreted as a chat prompt and actually invoked the model (see Evidence 1) — a
     real, if minor, "no introspection surface here" finding, discovered the hard way.
4. Read `~/.claude/settings.json` (this host's real, populated user-level hooks/mcpServers
   config), `~/.claude/plugins/cache/beadhive/bh/0.4.1/hooks/hooks.json` (a plugin-declared
   hook manifest using `${CLAUDE_PLUGIN_ROOT}`), and did a `find ... -iname hooks.json`
   sweep across every cached plugin to confirm `hooks/hooks.json` relative to a plugin's
   `installPath` is a load-bearing convention, not a one-off.
5. Wrote `docs/spikes/bh-8i03.1-resolved-state-probe.py` (stdlib-only Python 3, ~730 lines)
   funneling every "what binary does this refer to" question through one
   `resolve_binary()`/`BinaryRegistry` path, so MCP commands and hook commands are resolved
   the same way regardless of which config surface they came from.
6. Ran it repeatedly against this real, populated dev machine (not a clean/minimal
   sandbox) specifically because a noisy host is a harder test of "does the JSON actually
   stay stable" than a fresh one would be — this host has 41 installed plugins (24
   enabled), 9 MCP servers (2 of which are dead), and hook chains from five unrelated
   tools stacked in `~/.claude/settings.json`.
7. Verified the "zero self-delta" property empirically, not by inspection: ran the script
   four times back-to-back and diffed/hashed the outputs (Evidence 3). The *first* attempt
   at this actually failed — a real self-delta was found and fixed (Evidence 4) — which is
   itself the most important piece of evidence this spike produced.
8. Verified graceful degradation by re-running the exact same script with `claude` and `bh`
   both removed from `PATH` (Evidence 6), and under Apple's bundled `/usr/bin/python3`
   (3.9.6) instead of the mise-managed 3.12.13 interpreter this host normally uses
   (Evidence 7), to widen the "runs unmodified" claim beyond just "worked once in my shell."
9. Ran `uv run ruff check` / `uv run ruff format` against the script (this repo's own gate)
   and fixed everything it flagged, since the script lives in this repo and should pass the
   same bar as anything else here even though it is a spike artifact.
10. Did **not** attempt to acquire, provision, simulate, or containerize a Linux host — per
    this bead's explicit scope, that capture belongs to `bh-8i03.2` against a real machine.

## Evidence

### 1. `claude config` doesn't exist — an unrecognized subcommand becomes a chat prompt

```text
$ claude config list
It looks like your message just says "config" with no specific request attached. What
would you like to configure — Claude Code settings (permissions, hooks, env vars), a
project tool, or something else?
SessionEnd hook [...] failed: Hook cancelled
```

`claude --help`'s `Commands:` list (checked against v2.1.220) is: `agents, auth,
auto-mode, doctor, gateway, install, mcp, plugin, project, setup-token, ultrareview,
update` — no `config`. This is the first and most direct evidence for the "no CLI
introspection surface for effective settings" finding recorded in the probe's own
`unresolvable` list: there is no command to ask the harness for its own merged
settings.json view, and the failure mode when you try isn't a clean error, it's a live
(billed) model turn. This shaped the probe's design directly — see Evidence 8.

### 2. What DOES exist: three real introspection surfaces, one per required capture

| Requirement | Surface used | `--json`? |
|---|---|---|
| Plugins enabled (resolved) | `claude plugin list --json` | yes |
| Skills/agents/hooks per plugin (resolved membership) | `claude plugin details <id>` | **no** — text |
| MCP declared command + live connect status | `claude mcp list` | **no** — text |
| `bh`'s resolved workspace root / worktree shadow root / hives | `bh config show`, `bh hive list` | **no** — text |

Only `claude plugin list --json` (and, unused here, `claude plugin marketplace list
--json`) support machine-readable output. The other three are parsed from
human-formatted text, which is a real, load-bearing limitation, recorded verbatim in
the probe's `unresolvable` list — not silently worked around.

`claude plugin details bh` (the exact surface that answers "skills loaded, agents
available — resolved, not declared"), redacted-free because it carries no secrets:

```text
$ claude plugin details bh
bh 0.4.1
  ...
Component inventory
  Skills (16)  backfill, control, developer, dispatcher, groom, merger, overview, plan,
               planner, replan, retro, reviewer, setup, setup-git-workspace, triage, work
  Agents (11)  reviewer, analyst, merger, warden, developer, director, controller,
               dispatcher, planner, custodian, supervisor
  Hooks (2)  SessionStart, PreToolUse  (harness-only — no model context cost)
  MCP servers (1)  bh  (tool schemas resolved at runtime; not counted)
  LSP servers (0)
```

The probe calls this **only for plugins `claude plugin list --json` reports
`enabled: true`** — that is the literal implementation of "resolved, not declared": a
disabled plugin's skills/agents are not expanded, because they are not actually
available in a session. On this host, 41 plugins are installed; the probe's aggregate
output separately shows how many were enabled and expanded vs. disabled and skipped.

### 3. Zero self-delta, demonstrated (not asserted): four runs, one hash

```text
$ for i in 1 2 3 4; do python3 bh-8i03.1-resolved-state-probe.py > canon-$i.json; done
$ shasum -a 256 canon-*.json
a6af428df0faf47c987b53b53be3ee5f58f6776611bcb5b334fbefb1ba62affb  canon-1.json
a6af428df0faf47c987b53b53be3ee5f58f6776611bcb5b334fbefb1ba62affb  canon-2.json
a6af428df0faf47c987b53b53be3ee5f58f6776611bcb5b334fbefb1ba62affb  canon-3.json
a6af428df0faf47c987b53b53be3ee5f58f6776611bcb5b334fbefb1ba62affb  canon-4.json
```

Four independent invocations, same SHA-256, on a host with 41 plugins, 9 MCP servers, and
~400 environment variables. `json.dumps(..., sort_keys=True)` handles key ordering; every
list the probe builds (plugins, MCP servers, hooks, binaries, hive names) is explicitly
`sorted()` in code rather than trusted to arrive in a stable order from `claude`/`bh`.

### 4. The first attempt at Evidence 3 actually failed — the fix is this bead's best finding

Before the exclusion described below existed, the same four-run test produced:

```text
$ diff run1.json run2.json
389c389
<     "TRACEPARENT": "00-e615d3db8cb69e9291b4dcd3cd7be10f-ae930b0071e6bf8e-01",
---
>     "TRACEPARENT": "00-e615d3db8cb69e9291b4dcd3cd7be10f-7b87d76e84629340-01",
```

`TRACEPARENT` is the W3C trace-context env var: the trace id (`e615d3db...`) is constant
for the shell session, but the span id (`ae930b00...` → `7b87d76e...`) is regenerated
**per process launch** by whatever local tracing instrumentation stamps it into every
subprocess's environment. Nothing about host or harness *configuration* changed between
the two runs — this is session/process telemetry plumbing, not resolved state, and its
presence in a config-comparison instrument would have silently manufactured a fake delta
on every single comparison, forever, on any host where similar instrumentation runs. The
fix (`_VOLATILE_ENV_NAMES = {"TRACEPARENT", "TRACESTATE"}` excluded from `env.values`, but
named in `env.excluded_volatile_names` so the exclusion itself is visible, not silent) is
recorded in the script and mirrored in its `unresolvable` list. This is exactly the kind
of thing the epic's design warns a byte-diff approach would drown in noise — except here
it happened to the *resolved-state* probe too, one level down, until caught.

### 5. MCP connected-vs-declared: two real "declared but dead" cases, on the first run

From the actual `mcp_servers` section of `canon-1.json` (redacted where a real API key
appeared — see Evidence 9):

```json
{"name": "headroom", "connected": false, "status_text": "Failed to connect",
 "declared_command": "/Users/brian/.local/bin/headroom mcp serve",
 "error": "ENOENT: ENOENT: no such file or directory, posix_spawn '/Users/brian/.local/bin/headroom'",
 "binary": {"token": "/Users/brian/.local/bin/headroom", "resolved_path": null, "found": false, "method": "absolute-path"}}

{"name": "plugin:agentmemory:agentmemory", "connected": false, "status_text": "Failed to connect",
 "declared_command": "npx -y @agentmemory/mcp",
 "error": "-32000: MCP error -32000: Connection closed",
 "binary": {"token": "npx", "resolved_path": ".../bin/npx", "found": true, "method": "PATH-which"}}

{"name": "agentmemory", "connected": true, "status_text": "Connected",
 "declared_command": "npx -y @agentmemory/mcp@0.9.27", ...}
```

This is the exact case the bead calls out as "precisely the silent-miss case this entire
spike exists to catch": `headroom` is declared and its binary genuinely does not exist
(`found: false`) — a byte-level config diff across two hosts would show `headroom`'s
config as identical (or as a boring path difference) on both, and would never learn that
it doesn't run. `plugin:agentmemory:agentmemory` is a second, different failure shape:
its binary (`npx`) resolves fine, but the MCP *protocol* handshake fails — proving the
probe distinguishes "binary missing" from "binary present, service unhealthy," and that a
literally-identical MCP server declared two ways (directly in user settings vs. via a
plugin manifest) can have **different live outcomes** on the same host at the same
moment. Config-file identity would never surface either fact; asking `claude mcp list`
for its live-checked answer does, directly, with no precedence logic of this probe's own
in the loop.

### 6. Graceful degradation when `claude`/`bh` are absent from `PATH`

```text
$ env PATH="<python-dir>:<git-dir>:/usr/bin:/bin" python3 bh-8i03.1-resolved-state-probe.py
[probe] host + versions
[probe] claude doctor
...
[probe] done
$ echo $?
0
```

```json
"harness_claude": {"version": {"available": false, "reason": "not-found"}, ...},
"bh": {"available": false, "reason": "not-found"}
```

No traceback, exit 0, valid JSON with explicit `available: false` markers instead of a
crash. This matters because bh-8i03.2's Linux host is a real, independently-configured
machine whose toolchain shape is not guaranteed in advance — the probe has to survive
partial absence of the things it's trying to introspect, not just the happy path this dev
machine represents.

### 7. Ran successfully under Apple's bundled Python (3.9.6), not just the dev-managed one

This host's normal interpreter (via `mise`) is CPython 3.12.13; the script also ran,
unmodified, under `/usr/bin/python3` (Apple's system-bundled 3.9.6):

```text
$ /usr/bin/python3 --version
Python 3.9.6
$ /usr/bin/python3 bh-8i03.1-resolved-state-probe.py > syspy-run.json; echo $?
0
```

The output is structurally identical to the 3.12 run (same keys, same values) except for
`host.python_version` and a handful of extra environment variables that `mise`'s shim
injects around the interpreter it wraps when *that* interpreter is used instead (e.g.
`CPATH`, `LIBRARY_PATH`, `SDKROOT`) — itself a small, honest illustration of "the
environment a process sees depends on how it was launched," not a probe defect. This is
why the script uses `from __future__ import annotations`: without it, the `X | None`
union-type hints used throughout would raise `TypeError` at import time on Python < 3.10;
with it, annotations are never evaluated at runtime, so the same source runs on 3.9+
without a version gate.

### 8. Why Python (stdlib-only), not shell, given the bead's own coreutils/bash-4 warning

```text
$ /bin/bash --version | head -1
GNU bash, version 3.2.57(1)-release (arm64-apple-darwin23)
```

macOS ships bash 3.2 as `/bin/bash` (frozen there since Apple stopped shipping GPLv3
code) — no associative arrays, no `readarray`, materially different from any bash 4+/5
a Linux host would have. Combined with the `readlink -f`/`sed -i`/coreutils-flag
divergence the bead itself calls out, a bash implementation would have had to either
detect-and-branch on platform (reintroducing exactly the enumeration-not-generalization
problem the parent epic is about) or restrict itself to a bash-3.2-compatible subset
throughout. Python 3's standard library (`os`, `pathlib`, `shutil.which`, `json`,
`subprocess`) abstracts this class of difference away entirely, and `bh` itself is a
Python/`uv` project — any host capable of running `bh` already has a `python3` on
`PATH` by construction, so this is not an extra dependency being smuggled in.

### 9. This bead's own artifacts required active secret redaction — not a hypothetical

While building Evidence 2 and 5, `claude mcp list`'s real output on this host included a
live Context7 API key as a literal `--api-key` argument:

```text
context7: npx -y @upstash/context7-mcp --api-key ctx7sk-XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX - ✔ Connected
```

That value is real, live credential material this bead's own research surfaced —
confirming the design principle "prefer introspection" has a real cost: the tool being
introspected can hand back secrets unprompted. The probe redacts (`_SECRET_VALUE_RE`,
covering `sk-`/`ctx7sk-`/`ghp_`-shaped tokens, JWTs, and AKIA-style keys, plus any env var
whose *name* looks credential-shaped) before anything reaches its JSON output, and this
doc contains none of the real values — every example above is either redacted output or
hand-verified to be free of secrets before being pasted in. The `unresolvable` list
records this redaction as best-effort, not a guarantee.

### 10. `ruff` (this repo's own gate) passes clean

```text
$ uv run ruff check docs/spikes/bh-8i03.1-resolved-state-probe.py
All checks passed!
```

### 11. Explicit "cannot resolve" ledger (verbatim from the script's `UNRESOLVABLE` list)

1. No CLI surface merges settings.json precedence (Evidence 1); the probe reports each
   layer (`user_settings`, `user_settings_local`, `project_settings`,
   `project_settings_local`, `managed_settings_convention`) separately and unmerged.
2. `claude mcp list` and `claude plugin details` have no `--json` output in this CLI
   version; both are parsed from human-formatted, glyph-bearing text that a future CLI
   release could silently reshape.
3. The enterprise/managed-settings.json path (macOS:
   `/Library/Application Support/ClaudeCode/managed-settings.json`; Linux:
   `/etc/claude-code/managed-settings.json`) is a documented convention, not something any
   CLI surface confirmed — and neither file exists on this host, so the convention itself
   is existence-checked, not verified against a real instance.
4. Hook commands that are shell one-liners with conditionals (`if [ -f ... ]; then ...;
   fi`, seen on this host from three unrelated tools) are flagged `command_kind:
   shell-conditional` and not resolved to one executable — no shell grammar is parsed.
5. MCP `connected` status is a live health check at run time, not a static fact; it can
   legitimately differ between two runs if an underlying local server process itself
   changes state (this was distinguished from a real self-delta failure — see Evidence 4,
   which was a different, config-independent cause).
6. macOS Keychain-backed credentials have no filesystem-visible surface to probe at all;
   this bead does not attempt to enumerate them or their Linux equivalent (that's
   `bh-8i03.6`'s question).
7. This bead only ran the probe on macOS. Its Linux behavior is unverified here — that is
   `bh-8i03.2`'s job, against a real Linux host, per this molecule's own "no containers"
   constraint.
8. Secret redaction is a best-effort heuristic (Evidence 9), not a guarantee.

## Verdict — **GO**

The instrument works, on the one host available to this bead, against a real, noisy,
41-plugin/9-MCP-server development machine rather than a clean sandbox — the harder test.
Every acceptance criterion for this specific bead is met with direct evidence, not
assertion: stable-ordered JSON (Evidence 3), a real self-delta was found *and eliminated*
rather than assumed away (Evidence 4), MCP connect-vs-declared is distinguished with two
independently-caused live failure cases (Evidence 5), every config-referenced binary this
probe encountered resolved to an absolute path or an explicit not-found marker with zero
exceptions (Evidence 2, 5, and the full `binaries` section of any run), and the required
"what can't this resolve" list is explicit, sourced from real gaps hit while building the
probe rather than hypothesized in advance (Evidence 1, 11). No file under `src/beadhive/`
was touched; the only two artifacts this bead produced are this doc and the standalone
script beside it.

## Recommendation

For `bh-8i03.2`: run `docs/spikes/bh-8i03.1-resolved-state-probe.py` unmodified on the real
Linux host, capturing Linux **before** any provisioning touches it (per the epic's own
ordering constraint — that capture cannot be redone if gotten backwards). Expect, and do
not treat as probe bugs: different `host.hostname`/`platform_*` values (expected,
host-specific), a different `env.values` shape (real env differences are the point), and
possibly a fully-`available: false` `harness_claude` block if that host doesn't have
`claude` installed yet — the probe is designed to degrade to that gracefully (Evidence 6)
rather than crash, and a "harness not installed yet" result is itself valid baseline
evidence, not a failure to fix.

For `bh-8i03.3` (the classification-axis bead): the `binaries`, `mcp_servers`, and
`case_sensitivity` sections are what will actually get diffed across the two hosts'
outputs to populate the six-class axis (portable / path-translated / platform-substituted
/ host-specific / derived / unexplained) from the parent epic's design — this bead
deliberately did not attempt that classification itself, since it requires the second
host's data this bead's own scope excludes.

If a later bead productizes this into a `bh check`/`bh doctor`-style subcommand (gated on
`bh-8i03.7`'s GO), carry forward two concrete lessons from this spike rather than
rediscovering them: (1) anything derived from live process/session state (this bead found
`TRACEPARENT`; there may be others on a different host) needs an explicit exclude-list,
not an assumption that "nothing changed" implies "nothing in the environment changed"; and
(2) `claude mcp list`/`claude plugin details` text-parsing is a real, acknowledged
fragility (Evidence 2, 11) that a production version should either harden against a CLI
version check or push upstream as a feature request for `--json` support on those two
subcommands.
