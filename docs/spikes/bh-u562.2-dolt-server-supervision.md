# Spike `bh-u562.2` — Dolt and unified-host supervision on every plane

**Bead:** `bh-u562.2` · **Seat:** `dev/u562-supervision` · **Type:** research-only
(no product code)
**Feeds decision on:** `bh-u562.5`, the unified Beadhive host-daemon contract and its
implementation epic

## Question

Given `bh-u562.1`'s measured answer that bd's owned mode supervises its own Dolt server,
what—if anything—should supervise Dolt on macOS, Linux, and in the Beadhive image, and what
must report a dead server before an ordinary verb discovers it?

The epic was replanned after this bead was written. It now selects the unified ASGI process
proved by [`bh-u562.3`](bh-u562.3-unified-host-transport.md), so this spike must answer a
second, adjacent question without conflating the two processes: what supervises that one host
listener on each plane, what remains usable while it is down, and does its singleton scope
actually match Dolt and HQ?

This spike does **not** re-prove `.3`'s route composition, auth, session, or lifespan contract;
promote its scratch proof into product code; choose telemetry retention for `bh-u562.4`; or
re-answer `bh-ukit.2`'s lease/epoch-fence question.

## Method

The investigation used the merged `.3` tip (`6081d630`) and the repository's locked
environment. The exact unified-process boundary consumed here is:

- one Uvicorn/Starlette process and one outer lifespan;
- FastMCP's sessionful Streamable HTTP app at `/mcp`;
- versioned operator REST/SSE, terminal WebSocket, OpenAPI, and a public minimal `/health`
  route in that same process;
- SIGTERM stops new work, closes/cancels long-lived transports, exits the FastMCP lifespan,
  and completes within a ten-second bound; and
- existing CLI and `bh-mcp` stdio registrations remain direct, unchanged paths which do not
  depend on the daemon.

The exact `.3` proof command was:

```sh
.venv/bin/python docs/spikes/proofs/bh_u562_3_unified_host_transport.py \
  serve --port 8765
```

That command is evidence, not the future service `ExecStart`. The implementation epic must
add an installed product command and wrap the same composition/lifespan contract; no proof
file should be installed as a daemon.

### Isolation

All new Dolt measurements ran on Linux in `/tmp/bh-u5622-dolt-8335`, with:

```text
BEADS_SHARED_SERVER_DIR=/tmp/bh-u5622-dolt-8335/shared
BEADS_DOLT_SERVER_PORT=39382
database=u5622
bind=127.0.0.1
```

The experiment initialized a fresh local Git/bd project, never touched `~/.beadhive`,
`~/.beads/shared-server`, a registered hive's store, port 3308, or the live Beads port 3310.
Before SIGKILL, `/proc/3786792/cwd` was required to equal the scratch datadir exactly:

```text
verified scratch server pid=3786792 cwd=/tmp/bh-u5622-dolt-8335/shared/dolt
```

The server was restarted to prove recovery, queried successfully, and then stopped with
`bd dolt stop`. Reporting-surface checks used isolated `BH_HOME` and `GIT_WORKSPACE` trees
under `/tmp`; `bh doctor` and `bh hive ready` did not inspect or mutate the operator's real
home.

The available host was:

```text
Linux beadhive-factory 6.12.100+deb13-cloud-amd64 x86_64
bd version 1.1.0 (dev)
dolt version 2.2.3
```

No macOS host was available. No host was rebooted, slept, or deliberately filled. Those cells
are explicitly `UNMEASURED` below rather than inferred. The container plane was reasoned from
the checked-in Dockerfile and Compose contract; no image was built or container started.

## Evidence

### 1. Owned Dolt already has the lifecycle owner this bead was looking for

The canonical `.1` artifact is readable from the immutable commit with:

```sh
git show 6ebddf5c:docs/spikes/bh-u562.1-dolt-server-lifecycle.md
```

It measured an owned-mode server detached from the spawning bd process, then SIGKILLed it.
The next ordinary bd invocation transparently started a new PID on a new ephemeral port and
returned real data in 0.826 seconds. `.1` therefore answered its falsifier **YES**: owned mode
is durable enough that bh should not add a second Dolt lifecycle supervisor. Reboot and
sleep/wake remained `UNMEASURED`, but owned mode's recovery is lazy on the next invocation;
it does not require an idle server to survive reboot.

That conclusion is narrow. `.1` also measured that shared mode does not auto-restart and that
genuine external mode can create a dangerous empty shadow server if an operator follows its
misleading `bd dolt start` hint. This spike uses shared mode only to reproduce the down path
that Beadhive's current fleet observability targets; it does not widen owned mode's GO to
external mode.

### 2. A dead shared server hard-fails quickly and exactly; there is no fallback

The Linux scratch run initialized `bd init --shared-server`, verified a healthy SQL server on
127.0.0.1:39382, killed only its validated scratch PID, and ran:

```sh
bd list --status=open --json
```

The complete combined output and exit code were:

```text
Error: failed to open database: Dolt server unreachable at 127.0.0.1:39382: dial tcp 127.0.0.1:39382: connect: connection refused

The Dolt server may not be running. Try:
  bd dolt start
exit_code=1
```

`bd dolt start` then reported a new scratch PID (`3787218`), `bd list` returned `[]`, and
`bd dolt stop` stopped it cleanly. This reproduces `.1`'s shared-mode behavior against the
current binary: failure is fast, legible, nonzero, and does not silently open an embedded
store.

### 3. The old `.2` observability gap has already been implemented

Work that landed after `.1` already supplies the three reporting surfaces this bead's stale
brief says do not exist:

- `src/beadhive/dolt_health.py` probes the configured shared endpoint with a bounded MySQL
  handshake and never trusts bd's mode-dependent PID/status JSON.
- `src/beadhive/doctor.py` renders a fleet-wide **Store Engine** section, probes one shared
  endpoint once, inventories running Dolt processes, and distinguishes a reachable listener
  from a zombie whose datadir was deleted.
- `src/beadhive/setup.py` emits advisory `dolt-shared-server` without turning a moving
  operational fact into a failed binary/setup gate.
- `src/beadhive/hive_ready.py` emits the optional check named **`dolt server`**, also without
  changing AGF readiness.

The decisions and two-engine risk are recorded in
[`dolt-store-engine-liveness-adr.md`](../design/dolt-store-engine-liveness-adr.md). The current
Linux scratch measurements observed these exact results against the dead endpoint.

`bh setup check --json` still had `"satisfied": true` and included:

```json
{
  "id": "dolt-shared-server",
  "message": "⚠ dolt shared server unreachable: 127.0.0.1:39382 refused the connection — nothing listening\n    bd verbs against this hive will hard-fail until it's back — start it with `bd dolt start` (bh does not auto-start it or fall back to embedded)."
}
```

`bh doctor --json` included:

```json
{
  "store_engine": {
    "relevant": true,
    "endpoint": {"host": "127.0.0.1", "port": 39382},
    "server_mode_hives": ["bh"],
    "reachable": false,
    "detail": "127.0.0.1:39382 refused the connection — nothing listening"
  }
}
```

`bh hive ready -v` printed the optional line:

```text
! dolt server  127.0.0.1:39382 refused the connection — nothing listening — bd verbs will hard-fail until it's back; start it with `bd dolt start` (bh does not auto-start it or fall back to embedded)
```

The hive's final readiness exit was nonzero because the isolated fixture intentionally had no
HQ escalation parent, not because the optional Dolt warning became a gate.

One platform limitation is already encoded honestly: `dolt_health._proc_cwd` uses Linux
`/proc/<pid>/cwd` to attribute a server and detect an unlinked datadir. On macOS it returns an
unknown-but-not-missing datadir rather than manufacturing a zombie. Endpoint liveness remains
portable; full process/datadir reconciliation does not.

### 4. The unified ASGI process needs OS supervision; Dolt does not join its process tree

`.3` proved direct SIGTERM lifecycle and a post-lifespan marker, not restart across a crash.
The correct split is:

| responsibility | lifecycle owner |
|---|---|
| owned-mode `dolt sql-server` | bd, lazily and independently for each owned store |
| unified HTTP/MCP/operator/terminal listener | the platform service manager |
| HQ | passive store under `BH_HOME`; opened through existing fenced APIs, not exclusively owned by a process |
| CLI and stdio MCP | their invoking process, unchanged |

The ASGI daemon may **observe** Dolt and expose its health, but it must not parent Dolt, adopt
its PID, or auto-start it as a side effect of an HTTP request. Otherwise a listener restart
would become a database restart, and `.1`'s independent recovery boundary would be lost.

Likewise, “the daemon owns HQ” must mean it serves host-local HQ-derived views while alive,
not that it holds an exclusive lock or becomes the only path to HQ. `.3` explicitly keeps CLI
and stdio direct. Making HQ daemon-exclusive would contradict that compatibility result and
make every local verb depend on a new process.

### 5. Linux: `systemd --user`, but only after the host has a persistent user manager

The repository already has a real `systemd --user` implementation for unattended dispatch in
`src/beadhive/dispatch_supervisor.py`. It writes one template unit, uses an absolute bh
executable, requests restart, and reports installed/running/persisted state through one
structured computation reused by `bh doctor`. That is the right implementation pattern, but
its topology is deliberately wrong for this daemon: dispatch creates one instance **per
hive**, while the unified listener must have one instance per `BH_HOME` and route to many
hives.

This Linux host supplied a useful negative measurement. It has `systemctl` and `systemd-run`,
but the assigned user has neither a login session nor lingering:

```text
$ loginctl show-user 8335 -p Name -p State -p Linger -p RuntimePath
Failed to get user: User ID 8335 is not logged in or lingering

$ systemctl --user is-system-running
Failed to connect to user scope bus via local transport: $DBUS_SESSION_BUS_ADDRESS and $XDG_RUNTIME_DIR not defined (consider using --machine=<user>@.host --user to connect to bus of other user)
```

Therefore a user unit cannot even be stood up on this real headless host until provisioning
creates a persistent user manager (normally a logged-in session or explicitly enabled
lingering). Crash/restart and reboot persistence under systemd are `UNMEASURED` here; claiming
otherwise because the unit text looks right would be a vacuous pass.

**Recommendation:** use one `systemd --user` service for the designated Beadhive account and
make “user manager available and boot-persistent” a checked provisioning prerequisite. The
unit should use the future installed daemon command, an absolute executable, the configured
`BH_HOME`/`GIT_WORKSPACE`, restart on unexpected failure, startup-rate limiting, and a stop
timeout at least as large as `.3`'s ten-second shutdown bound. A headless operator who cannot
enable a persistent user manager must choose a system unit under a dedicated service account;
that root/admin cost must be disclosed rather than silently shipping a user unit which never
starts after reboot.

### 6. macOS: LaunchAgent for the designated account; literal machine-wide service costs root

No Darwin/launchd host was available. Launch, crash restart, logout/login, sleep/wake, and
reboot are all **UNMEASURED**.

The repository's existing supervision seam documents the matching implementation shape:
a per-user plist under `~/Library/LaunchAgents`, `launchctl bootstrap`/`bootout`, and
`launchctl print` for status, with `RunAtLoad` and `KeepAlive` covering launch and unexpected
exit. This is the recommended default because `.3` chose a per-user daemon and the daemon
needs that user's `BH_HOME`, workspace, and credentials.

A LaunchAgent is not a literal machine-wide, pre-login service. If “per host” is interpreted
to mean available before any user logs in, the mechanism is a LaunchDaemon/dedicated account,
which requires administrator installation and a deliberate credential/data-ownership design.
That is not the zero-root first-install default. The implementation epic must add a real-Mac
gate for bootstrap, SIGKILL restart, SIGTERM/lifespan completion, logout/login, sleep/wake, and
reboot before calling the LaunchAgent backend shipped.

### 7. Container: Compose is the supervisor; do not run a supervisor inside the container

The container result is **reasoned from source, not stood up**. `docker-compose.yml` currently
runs an interactive `bash` (`docker/Dockerfile` also declares `CMD ["bash"]`), keeps it alive
with `stdin_open`/`tty`, and sets `init: true` only to reap descendants. It has no restart
policy, daemon command, or healthcheck. `init: true` is not a service manager and does not
restart a dead child.

**Recommendation:** Compose (or the equivalent container orchestrator) owns one unified-daemon
service per Beadhive compose project. The ASGI command is that service's main workload under
the existing init/reaper, with `restart: unless-stopped`, an HTTP healthcheck against `.3`'s
minimal `/health`, and a stop grace period no shorter than the tested ten-second lifespan
bound. Keep interactive bootstrap/shell access as a separate concern; do not launch the daemon
as an untracked second background process beside the current interactive bash. The daemon
service can use the same durable `BH_HOME` and workspace volumes, but there must be only one
such service for that `BH_HOME`.

Container crash restart, Docker-daemon restart, host reboot, healthcheck transitions, and
volume-full behavior are **UNMEASURED**. The current file's comment about a missing
`compose.factory.yml` is not an implementation: no such file is checked in. Also,
`src/beadhive/templates/docker-compose.yml` is the older central `beads-db` stack, not the
unified image service, and must not be mistaken for the edit surface.

### 8. The singleton is per designated account/`BH_HOME`, not intrinsically per machine

`.3` recommends one **per-user** host daemon. The existing identity and storage facts align
with that narrower scope:

- `BH_HOME` owns the local `host.yaml`/`host_id` and HQ path;
- the user's configured `GIT_WORKSPACE` determines which hives the daemon can resolve; and
- bd's shared-server default, when used, is also under that user's `~/.beads`.

The precise v1 scope should therefore be stated as **one daemon per designated Beadhive
account and `BH_HOME`**. One machine can contain multiple OS users and multiple `BH_HOME`s;
they are separate Beadhive host identities unless provisioning deliberately selects one
dedicated account. Calling that fact “machine-wide” would promise discovery and credential
sharing the system does not provide.

The implementation must reject two daemon instances for the same `BH_HOME` through a
host-local singleton lock plus a local supervisor/control record containing the expected
`host_id`. After the minimal public health probe succeeds, identity can be verified through an
authenticated factory/status surface; `.3`'s public `/health` must not gain inventory. A fixed
port collision alone is insufficient evidence that the answering process belongs to the same
Beadhive home. A site that requires a literal one-per-machine service can enforce one dedicated
account and install the system-level service variants described above.

One process should **not** own both Dolt and HQ as exclusive children/resources. bd owns owned
Dolt lifecycle; HQ remains a passive, directly usable store; the daemon owns only its listener,
sessions, projections, and terminals. Telemetry/activity buffering remains `.4`'s decision.

### 9. Reporting contract, named by check

The current Dolt reporting is already the recommended contract and should not be replaced:

| surface/check | recommendation |
|---|---|
| `bh doctor` / **Store Engine** | Keep the fleet-wide endpoint probe, server inventory, zombie reconciliation, affected hives, and exact start remedy. It remains read-only and usable while both daemon and Dolt are down. |
| `bh setup check` / advisory **`dolt-shared-server`** | Keep liveness advisory-only. A moving service fact must not turn a valid binary installation into a failed setup gate. Preserve the image-manifest path's zero-subprocess contract. |
| `bh hive ready -v` / optional **`dolt server`** | Keep `ok`/`warn`/`na` and never make it a required AGF check. Embedded/owned lazy startup does not require an always-live idle server. |

The unified daemon needs a parallel but separate status vocabulary:

| surface/check | recommendation |
|---|---|
| future `bh host daemon status` | The single structured computation: configured scope (`BH_HOME` + `host_id`), supervisor backend, installed/running/persisted, `/health` reachable, and authenticated/local identity match. Every renderer consumes this rather than re-deriving health. |
| `bh doctor` / **Host Daemon** | Loudly distinguish not configured, installed-but-stopped, listener unreachable, wrong identity, and healthy. Always run locally; never require the daemon to diagnose itself. Include the platform start/status command. |
| `bh setup check` / **`host-daemon`** | Check structural prerequisites (installed product command, supported supervisor, user-manager/LaunchAgent/Compose availability). Runtime liveness is advisory and skipped on the zero-subprocess image-manifest path. Local CLI/stdio compatibility means daemon absence must not fail the core setup gate. |
| `bh hive ready -v` / optional **`host daemon`** | Warn when the daemon is configured for HTTP/operator use but unavailable; do not fail ordinary AGF readiness. A future explicit browser/remote readiness profile may make it required without changing today's local contract. |
| `/health` | Reuse `.3` exactly: public, minimal, no inventory or secrets. It is the supervisor/container probe, not a second diagnostics API. |

### 10. Down behavior is hard failure at the affected boundary, never implicit startup/fallback

“Hard-fail” describes the caller-facing boundary. The configured OS/Compose supervisor may
restart the daemon after an unexpected exit, but a CLI or client must not install, bootstrap,
or start a service as a side effect of an ordinary request.

| caller/path while unified daemon is down | v1 behavior |
|---|---|
| local `bh` CLI | Continues in-process against the same config/HQ/bd paths. |
| existing `bh-mcp` stdio | Continues unchanged; `.3` forbids redirecting it through HTTP. |
| MCP Streamable HTTP | Connection fails visibly; client retains no false session continuity and uses the platform status/start remedy. |
| operator REST/SSE/OpenAPI | Unavailable; browser shows a daemon-disconnected/refusal state and resnapshots after restart per `.3`'s cursor contract. |
| terminal WebSocket | Unavailable; any attached terminal is cancelled and descendants are cleaned up during the bounded shutdown contract. |
| activity POST | Unavailable at the listener. Whether producers retain/retry a bounded local record belongs to `.4`; this spike does not invent a queue. |
| HQ | Still accessible through local CLI/stdio paths; no daemon-exclusive lock or ownership transfer. |
| owned Dolt | The next bd-backed operation invokes bd's own lazy recovery independently. |
| shared Dolt | Existing bd verb fails with the exact exit-1 error above; existing reports warn. |

The choice is therefore **hard-fail at the affected transport, with OS-supervisor recovery**.
Bh does not auto-start Dolt or the daemon from an ordinary verb, and it never falls back from a
configured server store to embedded.

Falling back to embedded is rejected head on: it would create or resurrect
`.beads/embeddeddolt` while the configured server store still exists. Writes during the outage
would land in a different engine with no reconciliation path; when the server returned, the
operator would have two histories and no reliable answer to which wrote last. A visible outage
is recoverable. Silent split-brain storage is not.

### 11. Lease/epoch interaction recorded for `bh-ukit.2`, not resolved here

The scratch unified app serves inert fixtures, and the Dolt experiment used a local database
with no remote. No daemon/lease interaction was exercised; the result is **UNMEASURED**.

The process boundary nonetheless exposes one concrete handoff for `bh-ukit.2`: a long-lived
daemon gains no write authority merely by being healthy or holding sessions. Before any HQ or
per-hive mutation it must resolve the exact full hive identity, re-read the current host
lease/epoch through the same fenced path as a short-lived CLI verb, and refuse stale authority.
It must not renew every hive lease merely because `/health` is being polled, and a restarted MCP
session must not retain a pre-restart lease decision. This records the seam; `bh-ukit.2` owns
whether the shared/external transport itself satisfies the fence.

## Verdict — **GO**

Adopt a **split supervision contract**. Bd remains the sole lifecycle owner for owned-mode
Dolt on every plane; existing Store Engine/setup/readiness reporting already provides the
required pre-failure visibility and shared-mode hard-fail behavior. The unified listener is a
different process and is supervised once per designated account/`BH_HOME`: LaunchAgent on
macOS, `systemd --user` with an explicitly persistent user manager on Linux, and the container
orchestrator/Compose on the image plane.

The GO is conditional on implementation tests for the `UNMEASURED` platform cells above. It is
not evidence that launchd, systemd restart, reboot, or Compose recovery already works.

## Recommendation

`bh-u562.5` should ratify these consequences and file them as implementation work:

1. Add one installed unified-daemon command implementing `.3`'s exact routes, sessionful MCP,
   public minimal health endpoint, and single bounded lifespan. Do not install its proof.
2. Add a host-daemon supervisor seam shaped like `dispatch_supervisor` but keyed once by
   `BH_HOME`/`host_id`, not once per hive and not under `host.dispatch.backend`.
3. Ship and integration-test LaunchAgent, `systemd --user`, and Compose backends. Treat Linux
   user-manager/linger availability and macOS login-vs-boot availability as explicit setup
   facts, with a documented system-service escape for dedicated accounts.
4. Keep HQ directly usable and use a singleton lock plus an authenticated/local identity check
   to prevent two listeners for one `BH_HOME`. Keep public `/health` minimal, and do not infer
   machine-wide uniqueness from a port.
5. Keep the existing Store Engine reporting and no-fallback policy. Add the separate Host
   Daemon status/checks above without making local CLI or stdio depend on them.
6. Test daemon SIGKILL/restart, graceful SIGTERM, login/logout, sleep/wake, reboot, container
   restart/health, duplicate instance, wrong health identity, and bounded ENOSPC fixtures on the
   actual target planes. Every currently `UNMEASURED` cell stays a release gate rather than a
   prose assumption.
7. Carry the lease/epoch seam to `bh-ukit.2` and the activity retry/flush decision to
   `bh-u562.4`; do not silently decide either in supervision code.
