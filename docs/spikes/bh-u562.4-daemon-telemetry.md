# Spike `bh-u562.4` — what an always-on process buys over per-invocation OTel

**Bead:** `bh-u562.4` · **Seat:** `dev/u562-telemetry` · **Type:** research-only
(no product code)
**Feeds decision on:** `bh-u562.5`, the unified Beadhive host-daemon contract and its
implementation epic

## Question

Does telemetry, by itself, justify the unified host daemon selected by `bh-u562.3`? Concretely:
does today's short-lived CLI drop spans on normal exit, what does per-invocation OTel cost, which
questions genuinely require a long-lived process, and which have a cheaper answer?

This is not a second vote on `.1`'s owned-Dolt lifecycle GO, `.3`'s transport GO, or `.2`'s
supervision GO. It consumes their boundary: bd retains owned-Dolt lifecycle; one supervised
Starlette/Uvicorn lifespan owns sessionful HTTP MCP, operator REST/SSE, terminal WebSocket,
OpenAPI, and health; and the existing local CLI and stdio MCP remain direct, independent
processes. Telemetry can observe that chosen service; it cannot be credited with amortizing or
correlating traffic which never passes through it.

## Method

The measurements ran against source commit `6081d630` (merged `.3`) and were documented after the
bead branch fast-forwarded through `579d245` (merged `.2`) to `7d2b235` (reconciled merged `.1`;
none changed the telemetry code). The interpreter was the installed Beadhive OTel environment,
with Beadhive 0.14.0 and OpenTelemetry SDK/exporters 1.44.0, while `PYTHONPATH` selected this
checkout's `src/`.

### Isolation and counting

A scratch Python harness under `/tmp` created a temporary `BH_HOME` and `BH_CONFIG`, then bound an
ephemeral loopback gRPC port. Its instrumented receiver implemented the standard OTLP trace,
metric, and log `Export` services. It recorded every span from the server side, including trace
ID, parent ID, name, and Resource attributes. This is narrower and more deterministic than
querying Tempo: it counts what crossed the exporter/receiver boundary without search limits,
backend indexing delay, or unrelated traces.

Each child carried a unique `bh.spike.batch` Resource marker. The healthy drop workload ran 15
cycles of four read-only commands:

```text
bh config path
bh config schema --json
bh hive list
bh hive context
```

The expected count was one `bh.cli ...` root span per process, as established by
`cli.py:374-402`. Received roots were selected by the unique marker, an empty parent span ID, and
the `bh.cli` name prefix followed by a space. The receiver also accepted metric/log exports so
signal could not distort trace shutdown.

The claimed worktree has a legitimate `.bh/otel.env` for the operator's profile. An initial
trial which set only the scratch YAML endpoint was rejected as invalid evidence: the CLI's
documented non-clobbering worktree overlay redirected those children elsewhere. The final harness
explicitly set `OTEL_EXPORTER_OTLP_ENDPOINT` to its scratch port, which is the intended precedence
rule (`cli.py:350-370`). It touched neither that overlay nor the operator's home, collector, Dolt
server, live port 3310, or bead data.

For the unavailable case, the harness stopped that exact receiver and repeated the command with
the same address. All commands still exited zero. No timeout knobs were shortened: the point was
to measure the shipped SDK/exporter defaults.

### Timing

Every row used three warmups followed by ten timed fresh processes, matching the `bh-00cq`
addendum. The same checkout, interpreter, cwd, temporary config, and output capture were used.

- `--version` measured the eager, telemetry-free process floor; it exits before root telemetry
  initialization (`cli.py:350-357,431-442`).
- `config path` was the smallest real command which traverses root initialization, once with OTel
  disabled and once enabled against the healthy receiver.
- A fresh-process direct probe imported Beadhive first, timed only `otel.init(cfg)`, created one
  span, then separately timed `otel.shutdown()` against healthy and stopped receivers. This
  separates SDK construction from flush/export.

The historic ~140 ms floor in the molecule was not reproduced on this loaded Linux host: the
measured `--version` median was 943 ms. The measured local floor is therefore the denominator;
the old number is context, not substituted evidence.

## Evidence

### 1. Normal short-lived CLI exit dropped no measured root spans

| condition | expected roots | received roots | unique trace IDs | drop rate | command failures |
|---|---:|---:|---:|---:|---:|
| healthy loopback receiver | 60 | 60 | 60 | **0.0%** | 0 |
| receiver unavailable for the complete timed run | 10 | 0 | 0 | **100.0%** | 0 |

The healthy result answers the bead's primary bug question: **the present normal-exit path did
not drop spans in this run**. The implementation already retains all three providers, registers
`shutdown` with `atexit`, and shuts down each provider (`otel.py:97-105,411-458`). Adding another
`force_flush` is not the cheapest fix; on this path there is no measured loss to fix, and provider
shutdown already drains the batch processors.

The unavailable row has a narrower meaning. A process-local batch cannot deliver to a listener
which remains absent for its entire lifetime. The command outcome remains successful because
telemetry is best-effort, but all ten expected roots were necessarily lost. A daemon can retain
an in-memory batch across a short collector outage, but it still loses it on crash/restart and
does not create durable delivery. A local collector/agent with a persistent sending queue, or an
explicitly durable producer record, is the cheaper and correct durability boundary.

This experiment covers normal interpreter exit and a duration-complete collector outage. It does
not claim delivery after `SIGKILL`, power loss, kernel failure, or disk exhaustion; `atexit` cannot
run in those cases, daemon or no daemon.

### 2. OTel initialization is material, but healthy end-to-end overhead is smaller than it

| measurement (3 warmups + 10 runs) | min | median | comparison |
|---|---:|---:|---:|
| telemetry-free `--version` floor | 829.0 ms | **943.3 ms** | local startup floor |
| `config path`, OTel off | 768.4 ms | **883.0 ms** | real root callback, no SDK |
| `config path`, OTel on + healthy receiver | 987.6 ms | **1060.8 ms** | +177.8 ms / +20.1% vs off |
| direct `otel.init`, healthy receiver | 343.9 ms | **425.0 ms** | 45.1% of measured floor |
| direct `otel.shutdown`, healthy receiver | 6.2 ms | **6.7 ms** | one emitted span, all signals live |

The direct result proves provider/exporter construction is not free. A daemon initializes this
surface once per daemon incarnation, so requests through `.3`'s HTTP listener avoid that cost.
But `.3` and `.2` deliberately keep local CLI and stdio MCP independent. Their OTel initialization
continues once per process unless those compatibility contracts are later changed; the daemon
cannot claim that saving today.

The whole-process delta is the operator-visible tax for this lightweight command. It is smaller
than the separately timed `init` because these are independently sampled, noisy process paths,
not additive benchmark stages. Both establish the same direction without manufacturing false
precision: initialization is material, while process/import startup remains the larger local
floor.

### 3. An unavailable exporter exposes a timeout bug, not a daemon justification

| measurement (3 warmups + 10 runs) | min | median |
|---|---:|---:|
| direct `otel.init`, stopped receiver | 333.7 ms | **384.0 ms** |
| direct `otel.shutdown`, stopped receiver | 14,015.1 ms | **14,994.6 ms** |
| complete `config path`, stopped receiver | 21,935.8 ms | **24,044.3 ms** |

Endpoint availability barely affects construction; the large cost arrives during retry/export
and multi-provider shutdown. `shutdown()` catches exceptions, but its provider calls have no bh
deadline (`otel.py:440-455`). “Best effort” therefore preserves the command's zero exit status but
does **not** currently mean bounded exit latency.

This conflicts with `.3`'s requirement to close sessions/streams, flush telemetry, and finish the
whole daemon shutdown within a configured bound (`bh-u562.3-unified-host-transport.md:245-249`).
A 15-second telemetry shutdown alone cannot fit the proof's ten-second process envelope.

The cheapest fix is independent of daemon adoption: give CLI and daemon export a documented,
bounded budget using exporter timeouts plus a bounded `force_flush`, record whether it succeeded,
then continue shutdown when the budget expires. Do not serialize unbounded provider retry loops.
If delivery through outages is required, put a persistent queue in a local OTel Collector/agent;
do not turn the Beadhive HTTP daemon into a second telemetry collector.

### 4. Process identity becomes less noisy, but host identity does not appear by magic

A separate healthy sample ran ten fresh `config path` processes and inspected their received
Resources:

```text
received roots                 10 / 10
unique service.instance.id     10
resources with host.name        0
resources with bh.host.id       0
service.name values             ["bh"]
```

That matches the code: Beadhive explicitly stamps service/version, hive, role, worktree, profile,
and repo triplet, but not host identity (`otel.py:220-260`). A daemon naturally has one
`service.instance.id` for its process lifetime instead of one per command. That is useful as a
**daemon-incarnation** key and should change on restart. It is not stable host identity.

The cheapest stable fleet join is to add the existing `host.yaml` UUID as a low-cardinality
`bh.host.id` Resource attribute on both daemon and short-lived processes. `host.name` should remain
cosmetic: a rename or reused hostname is not Beadhive identity. Keep `service.instance.id` for the
incarnation and `bh.host.id` for the designated account/`BH_HOME` identity selected by `.2`.

There is one collector conflict to resolve. The current CLI metrics preset removes
`service.instance.id` from every `service.name=bh` metric stream so per-process delta metrics can
accumulate (`cli-metrics-preset.yaml:1-23`). If the daemon also reports as plain `bh`, that preset
erases the daemon incarnation which made the identity useful. The cheapest clear contract is a
distinct daemon service identity such as `service.name=bh-host-daemon`, with `bh.host.id` on both;
otherwise the preset must strip instances conditionally only for CLI metrics.

### 5. Cross-invocation questions: only daemon-lifetime state requires the daemon

| operator question today's telemetry cannot answer directly | daemon required? | what the daemon recovers | cheapest truthful answer |
|---|---|---|---|
| Which CLI commands belonged to one agent/operator work session, in causal order? | **No** | Nothing for unchanged CLI/stdio; `.3` keeps them outside the listener. | Propagate an explicit outer `run_id`/work-session correlation attribute from the existing run context/journal and use span links. Never infer it from `service.instance.id`. |
| What is a molecule's current progress across many invocations? | **No** | It can serve the projection while alive, but telemetry is not authoritative state. | Read the public bead snapshot/delta source and exact bead/epic IDs; use telemetry only for latency/error analysis. |
| Is Dolt continuously reachable, and is its connection pool saturated? | **No** for health; **only if created** for a daemon-owned pool | The daemon can expose its own dependency/pool gauges, but `.2` forbids it from parenting or exclusively owning Dolt. | Existing bounded Dolt probe plus OS/collector scheduling for continuous health. Instrument a pool only if the HTTP implementation actually creates one. |
| How much CPU/RSS does bh consume between CLI commands? | **No** | A daemon creates a continuous resource consumer to measure; there is no CLI process between invocations. | Per-invocation resource usage plus a host process exporter. Do not create an idle process to observe that no CLI process exists. |
| How many HTTP MCP sessions, SSE subscribers, terminal attachments, and slow/backpressured clients exist now? | **Yes** | These are live objects inside `.3`'s one ASGI lifespan. | Instrument the daemon which already owns them: active gauges, accepted/closed counters, queue depth, cancellation reason, and bounded labels. |
| Did activity published during a daemon outage reach the host? | **No** | The daemon cannot receive or report its own outage; `.2` says the POST boundary hard-fails while down. | Publisher retains/retries a bounded record with an idempotency key; the server durably appends before acknowledging and deduplicates. Count expiry/drop explicitly. |

The sole genuinely daemon-required row is observability of live state which exists only because
the daemon exists. That telemetry is an implementation requirement and operating cost of `.3`'s
chosen listener, not an independent reason to create it.

### 6. What the unified process should measure

Because `.3` and `.2` already justify and supervise the listener for non-telemetry reasons, its
implementation should initialize OTel once in the outer lifespan and cover:

- request spans/RED metrics by stable route template and protocol, never raw hive/run paths;
- active and total MCP sessions, SSE streams, terminal attachments, cancellation/disconnect
  reasons, bounded queue depth, and backpressure;
- daemon uptime/incarnation, graceful versus forced shutdown, restart count supplied by the
  supervisor, and telemetry flush success/timeout;
- dependency probe state for HQ/Dolt and any actual connection pool, without acquiring lifecycle
  ownership or write authority; and
- exact `bh.host.id`, hive identity, outer `run_id`, and authorization scope where appropriate,
  with no bearer values, task text, terminal bytes, or unbounded IDs on metric labels.

These signals fit `.3`'s single lifespan and `.2`'s one-daemon-per-designated-account/`BH_HOME`
scope. Public `/health` remains minimal; telemetry and authenticated diagnostics carry the detail.

### 7. Acceptance gaps exposed by the spike

The current unit tests prove that an atexit hook is registered and mocked providers receive
`shutdown`; the opt-in live harness proves signals can be inspected manually. Neither counts
emitted versus received CLI roots or bounds an unavailable exporter's exit latency. Downstream
work should add focused tests for:

1. zero healthy root-span loss across real fresh CLI processes;
2. a configured upper bound and explicit flush outcome with an unreachable receiver;
3. exactly one daemon init and one bounded shutdown per outer ASGI lifespan;
4. stable `bh.host.id` plus changing daemon-incarnation `service.instance.id` across restart;
5. the CLI-metrics preset not erasing daemon-incarnation metrics;
6. active-session/stream/terminal gauges returning to zero after cancellation and shutdown; and
7. activity retry/deduplication and an explicit drop counter after bounded retention expires.

No new product test or proof script belongs in this spike. Its only repository artifact is this
verdict document; the measurement harness and raw JSON were isolated scratch files under `/tmp`.

## Verdict — **NO-GO**

**No: telemetry alone does not justify a Beadhive daemon.** Healthy short-lived processes
delivered 60/60 measured root spans, and every missing cross-invocation answer except live
daemon-owned connection state has a cheaper explicit-ID, authoritative-state, probe, process
exporter, producer-retry, or collector-queue solution.

This does not reverse `.3` or `.2`. Their transport and supervision evidence independently selects
the unified listener. Once that listener exists, initializing OTel once and instrumenting its
lifespan is worthwhile; it is a consequence of the daemon contract, not its foundation.

## Recommendation

`bh-u562.5` should ratify telemetry as a bounded supporting concern:

1. **Keep the CLI independent.** Preserve current opt-in init and healthy atexit drain. Do not
   redirect CLI or stdio MCP through the daemon merely to amortize OTel.
2. **File the timeout bug separately.** Bound CLI and daemon flush/export, expose success/timeout,
   and fit daemon telemetry inside `.3`'s overall shutdown budget. Do not describe swallowed
   exceptions as a non-blocking path.
3. **Initialize once per daemon lifespan.** Add request/connection/dependency instruments listed
   above, with one shutdown coordinated by the outer lifespan and supervisor stop deadline.
4. **Separate host from process identity.** Stamp stable `bh.host.id`; retain
   `service.instance.id` as the daemon-incarnation key; use a distinct daemon service identity or
   update the metrics preset conditionally.
5. **Correlate explicitly.** Carry exact outer run/work-session IDs through HTTP and existing run
   context, using span links where traces cross process boundaries. Never join by PID, cwd,
   filename, prefix, MCP session ID, or `service.instance.id`.
6. **Keep durability outside the daemon's in-memory batch.** Use a local collector/agent persistent
   queue for OTel durability. For activity POST, require publisher-side bounded retry plus stable
   idempotency and acknowledge only after durable append; expose expiry/drop rather than silently
   losing records.
7. **Keep Dolt ownership split.** Reuse `.2`'s bounded health probe; instrument a connection pool
   only if the HTTP product creates one. Never start/adopt Dolt or renew authority from a health or
   telemetry loop.
