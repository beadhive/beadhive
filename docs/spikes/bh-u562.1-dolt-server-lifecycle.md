# Spike `bh-u562.1` — owned vs shared vs external: dolt server lifecycle and ownership

**Bead:** `bh-u562.1` · **Seat:** `dev/u562-1` · **Type:** research-only (no product code)
**Feeds decision on:** `bh-u562.5` (DECISION: does bh adopt a per-host daemon, and what does
it own?). This is the ROOT spike of the `bh-u562` molecule — `bh-u562.2` (supervise),
`bh-u562.3` (transport) and `bh-u562.4` (telemetry) all gate on this verdict for the dolt
half of the daemon question. Also feeds `bh-ukit.4` (target dolt mode for the fleet) and,
narrowly, the downstream `bh-areg` molecule's `.1` (HQ-backup) and `.2` (GH#2455-bootstrap)
beads, which are gated on this doc's data-location and bypass-count findings.

## Question

For each of bd's three server modes — **owned** (`bd init --server`), **shared**
(`shared-server: true` / `BEADS_DOLT_SHARED_SERVER=1`), and **external**
(`bd init --server --external --server-host H --server-port P`) — who owns the dolt
process, and what happens across its lifecycle: first start, concurrent access, crash,
sleep, reboot, upgrade, and shutdown mid-write? Embedded (bd's legacy in-process engine) is
the control arm throughout.

**The falsifier that matters most, stated as a yes/no question this spike must not hedge
on:** does `ServerModeOwned`'s self-management hold durably enough — surviving a hard crash
via transparent restart, cleaning up its own stale state, never stranding a port — that bh
needs **no daemon at all** for dolt lifecycle? A YES here is the cheapest possible outcome
for the whole `bh-u562` molecule: `bh-u562.2` (supervise) shrinks to an observability-only
question, and the daemon debate moves entirely onto whether HTTP transport or telemetry
justify one on their own.

Critically NOT asking: what shared mode SAVES across the fleet (disk, latency) — that is
`bh-ukit.1` and the `bh-00cq` addendum, cited below, not re-measured. Also NOT deciding
whether a shared/external server breaks the multi-host lease + epoch fence — that is
`bh-ukit.2`'s question; where this spike's experiments tripped over that boundary, it is
recorded under **Handoff to bh-ukit.2** below rather than resolved here.

## Evidence

### 1. Process ownership — server modes detach and outlive the spawning CLI; embedded does not

Source: `doltserver.go:924-1206` (`Start`) launches `dolt sql-server` via `exec.Command` with
`cmd.SysProcAttr = procAttrDetached()` (`doltserver.go:1124`), then `cmd.Process.Release()`s
it. On darwin, `procAttrDetached()` (`procattr_other_unix.go:16-18`) sets `Setpgid: true` —
"detach a child process from the parent process group so it survives parent exit... a shared
dolt sql-server must outlive the `bd` process that started it" (comment, same file).

Measured: right after `bd init --server` (owned) exited, `ps -p <pid> -o pid,ppid,pgid`
showed `PPID=1, PGID=<own pid>` — reparented to `launchd`, in its own process group,
listening (`lsof -iTCP:<port> -sTCP:LISTEN`). Identical for shared mode. For embedded,
running `bd list` while `pgrep -fl "dolt sql-server"` was watched showed **no new process at
all** — the engine runs entirely in-process inside the `bd` CLI and exits with it (confirmed
by `bd dolt status --json` reporting `"server_running": false"` with a populated
`data_dir_exists: true`).

For external mode, bd never spawns the process at all — I started the standalone
`dolt sql-server` myself, and it is untracked by bd's own PID file (`bd dolt status --json`
subsequently reported `"pid": 0, "running": false` even while the server was live and
answering real queries — see finding 9).

### 2. Restart semantics — owned auto-restarts fast; external's own suggested remedy is dangerous

Source: `EnsureRunningDetailed` (`doltserver.go:673-720`) is bd's auto-start entry point,
called from `newServerMode` (`store.go:1253-1350`) on every connection attempt that fails.
`IsRunning` (`doltserver.go:592-653`) self-heals a stale PID file (dead process → clears the
PID/port files, reports not-running) before `EnsureRunningDetailed` calls `Start()`. But this
whole path is gated: `resolveAutoStart` (`open.go:184-211`) hard-codes `mode ==
ServerModeExternal → always false`, and `ResolveServerMode` (`servermode.go:60-96`) resolves
**both** an explicit `--external` config **and** shared-server mode to the same
`ServerModeExternal` value — bd's own enum does not distinguish "shared" from "external" at
all; only "owned" is treated as bd's-to-restart.

Measured, owned: `kill -9` of the server PID (44176), then `bd list --status=open --json` —
completed in **0.826s wall clock**, exit 0, real data, with a **new** PID (50147) and **new**
ephemeral port (53747, was 53494). No warning, no visible restart ceremony — fully
transparent. This directly answers the "worse answer possible" concern the bead's brief
raised (embedded's historical 120s+ stall, see finding 3): owned mode's restart is not
merely non-hanging, it is *faster* than a cold `bd list` against a freshly-started server.

Measured, shared: `kill -9` of the shared server PID (45487), then `bd list` — **failed in
0.32s** with: `Error: failed to open database: Dolt server unreachable at 127.0.0.1:3308:
dial tcp 127.0.0.1:3308: connect: connection refused` plus `Try: bd dolt start`. Running
`bd dolt start` manually **did** correctly bring it back (0.7s, same shared data directory,
subsequent `bd list` succeeded, data intact) — shared mode's own state file bookkeeping
(`resolveServerDir`/`SharedServerDir`, `doltserver.go:251-263`) points `bd dolt start` at the
right place because it, too, is bd-managed, just centralized.

Measured, external — **the significant finding**: killing the standalone `dolt sql-server`
(PID 46546) and then running `bd list` produced the **identical-looking** error and the
**identical** `bd dolt start` suggestion. But `bd dolt start` (`cmd/bd/dolt.go:602-636`) has
**no check for `ServerModeExternal` at all** — unlike the auto-start path, this CLI command
unconditionally calls `doltserver.Start(serverDir)`. For a genuine external config,
`serverDir` resolves to the hive's own (empty, never-used) `.beads/dolt`, so it silently
**spawned a brand-new, empty shadow server**, bound to the very port (34001) the real
external server had just vacated. The next `bd list` then failed with `database "scrext" not
found on Dolt server at 127.0.0.1:34001` — a materially more confusing failure than "the
server is down," because *a* server answers on that port, just the wrong one, with none of
the real data. `bd doctor` correctly named the actual problem (`database not found:
scrext`), but its own suggested remedy (`bd dolt start`, echoed by the earlier error) is what
caused it. Recovery required restarting the **actual** external `dolt sql-server` on the same
host:port; once that was done, `bd list` succeeded with zero bd-side action (the direct
connectivity dial in `newServerMode` just started succeeding again). Source-confirmed root
cause: `doltStartCmd`'s `RunE` (`cmd/bd/dolt.go:602-636`) never consults `ResolveServerMode`,
unlike every other auto-start call site in the codebase.

### 3. Reboot / sleep — UNMEASURED by design; a structural argument, plus one field data point

No full reboot or sleep/wake cycle was performed. Putting this operator's own active machine
to sleep or rebooting it is out of proportion to a research-only spike and was not attempted;
this is exactly the kind of "stand it up for real, break it deliberately" work the sibling
spike `bh-u562.2` (supervise) is scoped and resourced to do on a dedicated machine/VM. Marked
**UNMEASURED** in the table below for all four modes, not inferred.

That said, two things are worth recording precisely rather than leaving as pure silence:

- **Structural argument for owned mode (source-based, not a substitute for a real test):**
  owned mode's recovery model is "lazy restart on next invocation" (finding 2), not "actively
  supervised while idle." A reboot kills every process, daemon or not; the question that
  actually matters is whether the *next* `bd` invocation in that project directory
  successfully restarts the server, and `IsRunning`'s dead-PID detection
  (`doltserver.go:611-617`) does not care *why* the PID is dead (crash, `kill -9`, or a
  reboot) — it just checks `isProcessAlive(pid)` and, if false, clears state and lets
  `Start()` run. The `kill -9` test in finding 2 exercises exactly this code path. This is
  stated as an inference from source plus the kill-9 result, explicitly not a substitute for
  `bh-u562.2`'s mandate to test an actual reboot/sleep cycle.
- **Incidental field observation (not engineered, not touched further):** a pre-existing,
  unrelated owned-mode dolt sql-server for a different local repo on this same machine has
  been running continuously since 2026-07-09 (PID 47760, `ps -o lstart,etime` showed
  `Thu Jul 9 18:50:19 2026`, 24+ days elapsed at time of writing). This is consistent with
  (does not prove) surviving repeated sleep/wake cycles on a daily-use laptop, and it also
  means this machine has evidently not been fully rebooted in that window — so it says
  nothing about surviving an actual reboot, only that reboots are rare in practice compared
  to sleep, which is itself a useful calibration for how `bh-u562.2` should weight its own
  test plan.

### 4. Port allocation — owned is collision-proof; shared/external share a fixed default port

Source: owned/default mode allocates via `allocateEphemeralPort` (`net.Listen(":0")`,
`doltserver.go:340-348`) — "Port assignment uses OS-assigned ephemeral ports by default...
eliminates the birthday-problem collisions that plagued the old hash-derived port scheme"
(module doc, `doltserver.go:5-9`). Shared mode uses a fixed `DefaultSharedServerPort = 3308`
(`doltserver.go:92`) precisely to avoid GT-orchestrator's 3307 (comment, same file). Explicit
ports (shared's fixed default, or external's operator-chosen port) go through `reclaimPort`
(`doltserver.go:371-404`): if busy, identify the PID, and refuse with a specific message
unless the process is provably "ours" (same data-dir CWD).

Measured, owned: with the first owned-mode server still running on port 53747, a **second**
independent owned-mode project (`bd init --server --prefix scrown2`) got port **54505**,
zero collision, zero manual intervention, zero warning.

Measured, shared — directly answers "two bh installs or a container and a host both wanting
one": with the first shared server live on port 3308 (via `BEADS_SHARED_SERVER_DIR=.../home`),
pointing a **second, independent** shared-server home
(`BEADS_SHARED_SERVER_DIR=.../home-2`) at the same default port failed **cleanly and
legibly**: `Error: failed to start shared Dolt server: cannot start dolt server on port 3308:
port 3308 is in use by another project's dolt server (PID 50972).` with concrete remediation
(point at the existing server via `BEADS_DOLT_SERVER_HOST`/`PORT`, or `bd dolt set port`).
Nothing was silently corrupted; the partial init left only an empty `.gitignore`, no `.beads`
was ever created. External mode shares the identical `reclaimPort` code path for its
operator-chosen port, so the same refusal shape applies there by construction (not
independently re-tested, since it is the same function).

**A vestigial, unenforced ceiling, found in source but not empirically stress-tested past
N=6:** `maxDoltServers()` (`doltserver.go:332-334`) documents "the hard ceiling on concurrent
dolt sql-server processes. Allows up to 3" but has **no call site anywhere in production
code** (only its own two unit-test references, `doltserver_test.go:499,508`). Empirically,
this spike had **six** simultaneously-running `dolt sql-server` processes at one point
(2 owned + 1 shared + 1 external + 1 supplementary plain-init owned + 1 pre-existing
unrelated one) with no warning, refusal, or enforcement of any kind — confirming the
doc-commented ceiling does not actually bind. This is a real, unbounded per-host process-
sprawl cost for owned mode specifically: every distinct project directory using owned mode
gets its own permanent background `dolt sql-server`, forever, with nothing counting them.

### 5. Concurrency — the previously-unmeasured argument, now measured

`N=5` concurrent readers (`bd list --status=open --json`) + 1 concurrent writer (5
sequential `bd update`), wall clock, 3 runs per mode:

| mode | run 1 | run 2 | run 3 | min / median |
|---|---|---|---|---|
| embedded | 4.109s | 3.456s | 2.739s | 2.739s / 3.456s |
| owned | 0.919s | 0.768s | 0.597s | 0.597s / 0.768s |
| shared | 0.712s | 1.038s | 0.720s | 0.712s / 0.720s |
| external | 0.750s | 0.772s | 0.834s | 0.750s / 0.772s |

Embedded is **4-5x slower** than any server mode under this concurrency shape on identical
300+MB data, even though nothing in this run held a lock for long (see below) — most of
embedded's cost here is repeated engine-open overhead across 6 concurrent processes, not
lock contention specifically.

**A second, much sharper, single-process (zero concurrency) comparison** using
`bd label list-all --json` alone — the exact command `bh-00cq` named as one of the ones that
stalled 120s+ under contention:

| mode | `bd label list-all --json`, alone, no concurrency |
|---|---|
| embedded | **36.336s** |
| owned | 1.262s |
| shared | 1.073s |
| external | 1.360s |

A **~29x** difference on identical data with zero concurrent contention at all. This is a
new, sharper, more controlled number than `bh-00cq`'s addendum table (which covered
`bd ready`/`bd list`/`bd stats`/`bd show`, all lighter commands with a 2-4x spread) — full
table-scan-shaped commands amplify the embedded-vs-server gap substantially.

**Attempted, explicitly not reproduced:** running `bd label list-all --json` in the
background and firing a concurrent `bd list --status=open --json` against embedded mode
completed in 1.1s — no multi-second stall observed. Two different angles (this test, and the
5-readers-+-writer table above) both failed to reproduce `bh-00cq`'s anecdotal 120s+ stall
(`bh plan repair`/`bh plan verify`/`bd label list-all`). This is recorded as an honest
non-reproduction, not a refutation — plausible explanations (untested, not claimed):
`bh plan repair`/`verify` are bh-level operations doing much more work under a single held
transaction than this spike's synthetic writer; the anecdote may be scale- or version-
dependent; or the stall requires a genuinely long-held *write* transaction this spike's
5-short-sequential-writes shape never produced. Whatever its cause, embedded's `bd label
list-all` being 36s **by itself**, with no concurrency at all, is independently damning
regardless of whether the specific lock-stall anecdote reproduces.

### 6. Per-database isolation under shared mode — a held connection did not block a sibling DB

A second database (`scrshr2`) was created on the same shared server as `scrshr`
(`bd init --shared-server --prefix scrshr2`, same `BEADS_SHARED_SERVER_DIR`). With a
background `bd sql "SELECT SLEEP(6)"` held open against `scrshr`, a concurrent `bd list
--status=open --json` against the sibling `scrshr2` completed in **0.151s**, fully
unaffected. This supports (for this specific scenario) that ordinary connection-level
contention does not cross database boundaries on a shared server.

**Explicitly UNMEASURED, not extrapolated from the above:** an in-flight schema migration or
a genuinely corrupted database's effect on sibling databases on the same shared server.
Reproducing a realistic corruption safely was outside this spike's time budget. This remains
a real, named, open question for `bh-ukit.4`'s decision if shared mode is a fleet-default
candidate — the molecule's own design doc already names the concrete risk (`bh-wnly`: "under
a shared server one bd upgrade advances every database's schema at once").

### 7. GH#2455 — zero bypasses via the mandated cold-clone recipe; reproduces under a plain init

Immediately after each cold-clone init (`--remote git+ssh://...`), `bd sql "SELECT * FROM
dolt_status"` returned `[]` (clean) for **owned, shared, and external** — before running any
other command, including `bd dolt commit`. **Zero GH#2455 bypasses were required** across all
three server modes when seeded via the design doc's own mandated recipe. (Embedded does not
support `bd sql` at all: `Error: 'bd sql' is not yet supported in embedded mode`.)

This differs from `bh-00cq`'s finding, and the difference is precisely why it is worth
recording rather than silently favoring one result: `bh-00cq`'s GH#2455 repro (Method step 3)
used a **plain, non-clone** `bd init --server --external ...`; its cold-clone variant (step
8) was only used to test transfer speed, and dirty-config status was never re-checked on that
specific path. To confirm this is a real seeding-method effect and not a fluke, this spike
additionally reproduced `bh-00cq`'s exact method in a fifth scratch dir
(`bd init --server --prefix scrplain --non-interactive`, **no** `--remote`):
`dolt_status` immediately showed `[{"staged": 0, "status": "modified", "table_name":
"config"}]` — the classic bug, reproduced exactly. `bd dolt commit -m "..."` printed
`Committed.` while `dolt_status` **still** showed the same dirty row afterward — confirming
no bd-native command clears it. The documented bypass (`bd sql "CALL DOLT_ADD('-A')"` then
`bd sql "CALL DOLT_COMMIT('-m', ...)"`) cleared it in exactly **one** application
(`dolt_status` → `[]` afterward).

**Bottom line for `bh-areg.2` (GH#2455-bootstrap):** the bug is real and the bypass is real,
but it is specific to a **fresh, non-clone** server-mode init — the recipe this spike (and
presumably any first-install-via-clone path) actually used avoids it entirely. If bh's
eventual first-install flow clones from a remote (as `bh-areg.7`'s own text, encountered
incidentally in the cloned production data used for this spike, already assumes it will —
mentioned only in passing per this bead's scope boundary on `bh-areg`), GH#2455 may not be a
first-touch problem at all; if it ever inits fresh-without-a-remote for any server mode, the
bypass is mandatory and no bd-native command performs it.

### 8. On-disk store location per mode, and what the four hardcoded call sites get right/wrong

| mode | actual store location (measured) |
|---|---|
| embedded | `<hive>/.beads/embeddeddolt/<db>/` (e.g. `.../embedded/.beads/embeddeddolt/scremb/`, 324MB) |
| owned | `<hive>/.beads/dolt/<db>/` (e.g. `.../owned/.beads/dolt/scrown/`, 340MB) — **not** `embeddeddolt` |
| shared | `~/.beads/shared-server/dolt/<db>/` (or `$BEADS_SHARED_SERVER_DIR/dolt/<db>/`), **centralized, outside any single hive's directory tree**, shared by every project's own database on that host |
| external | wherever the external server's own `--data-dir` points — **may be on a different host entirely**; the hive's local `.beads/dolt/` is empty (confirmed: only `.doltcfg`/`.dolt` bootstrap scaffolding, 0 real data) |

- **`hq.py:759`** — `src = hq_dir / ".beads" / "embeddeddolt"`. For owned/shared/external
  this path never exists (confirmed above). **Safe by construction**: `_backup_tar` checks
  `src.is_dir()` directly against the filesystem (not a parsed mode string), so it correctly
  falls to `_absent_store_reason()` and reports the backup target as **UNAVAILABLE** rather
  than silently "succeeding" on an empty directory — the exact bh-kobw failure mode this code
  exists to prevent. The one weakness: `_absent_store_reason` (`hq.py:741-755`) calls
  `safety._bd_dolt_mode()`, which parses the `"mode"` key from `bd dolt status --json` — and
  that key is **present** for embedded (`"embedded"`) and shared (`"external"` — see below),
  but **absent entirely** for owned and (local) external mode's status JSON (measured
  directly, finding 9). So for owned/external, `_absent_store_reason` falls into its
  `mode is None` branch and reports the generic "bd could not report HQ's dolt engine mode"
  rather than the more precise "HQ's dolt engine is in 'X' mode" message — functionally safe
  (never a false success), just less informative for those two modes specifically.

- **`hq_restore.py:36-37`** (`_STORE_REL = .beads/embeddeddolt`) — same wrong path
  assumption, but here the consequence is a **real bug, not just an imprecise message**.
  `restore()` (`hq_restore.py:103-140`) computes
  `tar_usable = mode is None or mode == "embedded"` (`hq_restore.py:116`). Because
  `_bd_dolt_mode()` returns `None` for **both** owned mode and (local) external mode's status
  JSON (measured, finding 9 — not a hypothetical), this line currently treats "bd could not
  tell us the mode" as equivalent to "confirmed embedded, tar is safe" for those two modes.
  A restore attempted against a live owned- or external-mode HQ would proceed with the tar
  level and extract into `.beads/embeddeddolt` — a directory the running engine never reads
  — reporting a "successful" restore that silently restores nothing, which is exactly the
  bug the surrounding code's own comment (`hq_restore.py:125-133`) says it exists to prevent.
  Shared mode is **not** affected by this specific bug, because shared mode's own
  `bd dolt status --json` **does** expose `"mode": "external"` (measured), so `tar_usable`
  correctly evaluates `False` there. **Minimum fix to record, not implement:** tighten line
  116 to `tar_usable = mode == "embedded"` (drop the `mode is None` half), or positively
  confirm via `data_dir`/`data_dir_exists` rather than trusting the mode string's presence.

- **`host_fence.py:64`** (`_DOLT_TRANSPORT_GLOB = "embeddeddolt/*/.dolt/git-remote-cache/*/repo.git"`)
  — the git-transport bare repo this glob looks for **does exist** under every server mode,

  - external: confirmed at `<external's own --data-dir>/scrext/.dolt/git-remote-cache/<hash>/repo.git`

  ALSO push from within that nested repo rather than from the hive's own — which would mean
  the hive's-own-`.git/hooks` install never actually fires for a real `bd dolt push` under

  below, since the consequence (if true) is squarely a multi-host lease/fence gap, not a

### 9. `bd dolt status --json` shape differs by mode; misreports a healthy external server as down

Measured JSON shapes, same command, four modes:

```text
embedded: {"data_dir": "...", "data_dir_exists": true, "mode": "embedded", "schema_version": 1, "server_running": false}
owned:    {"data_dir": "...", "pid": 50147, "port": 53747, "running": true, "schema_version": 1}
shared:   {"database": "scrshr", "host": "127.0.0.1", "mode": "external", "port": 3308, "running": true, "schema_version": 1, "tls": false, "user": "root", "version": "8.0.31"}
external: {"data_dir": "", "pid": 0, "port": 0, "running": false, "schema_version": 1}
```

Three distinct shapes, and only two of the four expose a `"mode"` key at all (feeding
finding 8's `hq_restore.py` bug directly). Source (`cmd/bd/dolt.go:683-836`) explains why:
`shouldUseExternalDoltStatus` routes shared mode (and any non-local-host or
auto-start-disabled server config) to a SQL-ping-based status render
(`runExternalDoltStatus`, the shape with `"mode": "external"`), but a **local**-host
`--external` config with auto-start *not* explicitly disabled — exactly this spike's external
setup, and plausibly a common real one (an operator's own locally co-located dolt
sql-server) — falls through to the **local PID-file path** instead
(`renderLocalDoltStatus`), which has nothing to report because bd never wrote a PID file for
a server it didn't spawn. This is why `bd dolt status` reported `"running": false"` for the
external scratch dir throughout this spike **even while the server was live and answering
real 16K-line `bd list` queries** (confirmed side-by-side, finding 2's recovery test). This
is bd's own bug, not bh's, but it directly undermines any bh-side tooling (`bh doctor`,
future supervision) that would otherwise trust `bd dolt status --json`'s `running` field for
a locally-hosted external server.

## Handoff to bh-ukit.2

Two findings above are squarely multi-host lease/epoch-fence territory (`bh-ukit.2`'s
mandate), not this bead's to resolve — recorded here rather than silently ignored or decided:

1. **`host_fence.transport_repos()` cannot locate the git-transport bare repo for shared or
   external mode at all**, because that repo lives entirely outside `hive_dir` (under
   `~/.beads/shared-server/` for shared, or on the external server's own, possibly
   remote, data directory). The epoch fence's own push mechanism
   (`docs/design/multi-host-model-adr.md` Amendment 1 §2, `git push --atomic ... origin
   refs/dolt/data refs/bh/epoch`) is documented as needing to run from *inside* that bare
   repo (`host_fence.py:150-166`) — if shared/external modes never get their bare repo
   discovered, the fence mechanism as currently wired may have nothing to run from under
   those modes. This spike did not attempt to resolve it — it is squarely `bh-ukit.2`'s
   question, and now has concrete file:line + measured-path evidence to start from.
2. **Whether `bd dolt push`'s actual `git push` invocation happens from the hive's own repo
   or from the nested transport-repo, under owned/shared/external mode, is unknown** (this
   bead's hard constraint forbids ever invoking `bd dolt push` to check). If it is the
   latter (as the existence of an identically-structured nested bare repo under every server
   mode suggests, though does not prove), `prepush.py`'s pre-push fence hook — the
   defense-in-depth in front of the real epoch fence — may never fire for any server mode
   today. Flagged for `bh-ukit.2` to resolve with an instrumented (non-push) test or a
   direct read of bd's own push-path source, rather than resolved here.

## Verdict — **GO**

**The falsifier, answered plainly: YES.** `ServerModeOwned`'s self-management is durable
enough that bh needs no daemon for dolt lifecycle under owned mode specifically. The
concrete enablers, all measured on this machine against this exact bd binary: the spawned
server detaches and survives its parent CLI's exit (finding 1); a hard `kill -9` is followed
by a transparent, sub-second restart with a fresh PID and port, strictly *better* than
embedded's own historical worst case (finding 2); port allocation is collision-proof by
construction, not merely collision-avoidant (finding 4); and the lazy-restart-on-next-use
architecture structurally does not depend on anything surviving a reboot to keep working
(finding 3) — though an actual reboot/sleep test remains `bh-u562.2`'s explicit mandate, not
inferred here.

**This is the cheapest possible outcome named in the epic's own design doc, and it held.**
`bh-u562.2` (supervise) can shrink to an observability-only question for owned mode, exactly
as its own bead text anticipates. `bh-u562.3` (transport) and `bh-u562.4` (telemetry) are
unaffected either way — they justify a daemon (or don't) on entirely separate grounds.

**A sharp, load-bearing caveat that must travel with this GO, not be smoothed away:** the
YES above is about **owned mode specifically**, because that is the literal question asked.
It does **not** extend to shared or external modes, which bd's own `ResolveServerMode`
(`servermode.go`) treats as a single, different `ServerModeExternal` category with a
materially worse restart story: no auto-restart at all (fails fast, requires an operator or
something else to notice and act), and — for genuine external mode — bd's own suggested
remedy (`bd dolt start`) is actively dangerous (creates a silent shadow database on the
vacated port, measured). If `bh-ukit.4`'s eventual fleet-mode decision favors shared mode
(which `bh-ukit.1`'s savings analysis may push toward), the daemon question is **not**
settled by this GO — a health-checking, restart-capable supervisor becomes a live argument
again, specifically for shared/external, not for owned. This spike answers the literal
falsifier; it does not launder that answer into "no server mode ever needs a daemon."
